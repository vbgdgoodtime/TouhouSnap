# 联机对战（实时房间 / 挑战码 / 重放）· 当前口径

> 本文件是**联机相关内容的专项文档**：实时房间（联网对打）、一局的完整输入、挑战码格式、重放的两种模式与探针。
> 两条路子都已实装，且共用同一套"确定性重算"的地基：
> - **实时房间**（主页面「🌐 联机对战」）＝云上一台只转发消息的房间（`worker/`），对局跑在两端浏览器里，每回合交换一次动作；
> - **挑战码**（结算弹窗「📤 生成挑战码」/ 主页面「🔗 挑战码」）＝把一局烘焙成一行文本码，另一端凭码把整局重算出来（零后端）。
> 玩家入口：主页面「🌐 联机对战」（房间弹窗 `#netMask`）、主页面「🔗 挑战码」与结算弹窗「📤 生成挑战码」（`#challengeMask`）；
> 对局中另有顶栏状态条 `#netBar`（房间码 / 对手在线 / 提交与对账状态）。
> 改动一律遵守 `docs/开发规则.md`（规则 1 只写当前内容、先精简；规则 6 验证由用户负责）。

## 1. 为什么每一局都能被复现

**一局的完整输入 = 种子 + 双方卡组 + 建牌路径 + 数据版本 + 双方每回合的动作。**

- **种子**：`restart` 每次开局都重新播种（`opts.seed` 不传就取一个新的随机种子）⇒ 每局都不同、每局都可复现。
- **两条互相独立的随机流**：`rng()`＝主逻辑流（洗牌 / 抽地形 / 翻牌先后 / 掷骰 / 并列取谁 / 随机取牌）；
  `aiRng()`＝只给 AI 决策用。**必须分开**：AI 的随机不属于"一局的输入"——同一个种子 + 同一串动作必须算出同一局
  （挑战码重放、联机两端对账都靠这一条）；AI 若把主逻辑流吃走，整条随机流的位置就会随 AI 的思考次数漂移。
  阶段③ 把全局 `Math.random` 临时换成 `aiRng`（期间不碰主逻辑流），未播种时不做任何替换；
  AI 抛异常不放任打死整局，而是打印完整错误后按"它已放下的牌"继续这一回合。
- **表现随机**（粒子 / 飘字 / 装饰）仍走原生 `Math.random`，不参与复现。
- **建牌路径是输入的一部分**：自建 12 张（`buildDeckFromDefs`，只洗 1 次）与费用曲线随机组
  （`buildDeckCards`，每个费用档各洗一次 + 再洗一次曲线）**消耗的随机数个数不同**——走错一条，后面整条随机流就错位，
  对手牌组与三块地形全都会变。
- **自建 12 张的牌不能"再洗一遍"**：`buildDeckFromDefs` 的洗牌输入是**玩家选的顺序**，而记录里存的是**洗完之后**的数组顺序
  ⇒ 重放必须按记录顺序**直接建牌**（`buildDeckInOrder`：不洗，但**照样消耗掉那 11 次随机数**，并按记录的倒序建牌以还原卡牌 id）。
  否则会得到"牌一样、顺序不同"的牌组——**对手牌组与地形都一致，唯独我方起手不同**。
- **卡组顺序与卡牌 id 都是复现目标**：id 按建牌顺序分配、起手按牌库顺序抽，顺序不同 ⇒ 整局分叉。

## 2. 挑战码格式

```
TH2P2:<种子>:<数据哈希>:<建牌路径>:<我方卡组>:<对方卡组>:<逐回合动作>
```

| 字段 | 口径 |
| --- | --- |
| 种子 | 十进制 |
| 数据哈希 | `Game.dataHash()`：8 位十六进制，来自**数据内容**（卡池 / 特殊卡 / 阵营分组 / 地形），不含引擎代码 |
| 建牌路径 | 1 字符：`d` 自建 12 张 / `c` 费用曲线随机组 / `e` 开发调试空牌库（`e` **既不生成也不接受**挑战码） |
| 卡组 | 12 项、`-` 分隔，每项 `费用.该费用档内的下标`（中文卡名直接进码会显著变长；下标依赖 data 顺序，已由数据哈希兜住） |
| 逐回合 | `\|` 分隔；每回合 9 个 `:` 字段：回合号、我方落牌、我方移动、我方本回合是否宣布加倍、我方是否撤退、对方落牌、对方移动、对方本回合是否宣布加倍、对方是否撤退 |
| 加倍 / 撤退项 | `1` / `0`（每方整局各只能加倍一次，所以这两项都是 0/1，不需要记数值） |
| 落牌项 | `卡id.区域`；开发调试「敌方立场」落牌追加 `A`（该牌归属对手） |
| 移动项 | `卡id.来源区域.目标区域`（`fly`，如射命丸文） |
| 列表分隔 | 同一字段内多项以 `,` 分隔 |

- **赌注值本身不入码**：结算值与「撤退价」都由「谁在第几回合宣布加倍」按同一套规则派生（`docs/GAME_REFERENCE.md` §3），两端各算一遍、不会各存一份数——少一个可以互相矛盾的字段。
- **旧版 `TH2P1` 码一律拒绝**（每回合 7 字段、带单一赌注值，与新赌注口径对不上），提示"请对方用新版重打一局生成新码"。

**校验**：前缀、字段数、模式字符、每一项的格式任一不过关 ⇒ 解码返回 `null`；
**数据哈希不同直接拒绝**并提示"请双方刷新后再试"。

## 3. 重放的两种模式

| | 复盘（`mode: 'review'`） | 同一局面挑战（`mode: 'shadow'`） |
| --- | --- | --- |
| 我方动作 | 取自记录（不等玩家） | 玩家实时操作（可正常出牌、加倍） |
| 对手动作 | 取自记录 | 取自记录（即「影子」） |
| 玩家座位 | — | 原局我方的座位：同一副卡组、同一副起手、同样地形 |
| 打完能否再生成码 | 不重录（`Game._code()` 仍返回原局那行码） | 能（朋友可回传自己的打法，码同样可被完整重放） |

- **「同一局面挑战」不是「各带卡组的对战」**：影子依赖确定性重放，双方的**卡组与种子都必须与原局一致**——
  影子当时那些"卡 id + 区域"的动作只在原局的盘面上成立。各带卡组的真人对打走**实时房间**（见 §5）。
- 重放的**状态改动**与玩家点牌落子 / `aiThink` 等价：进区、进放置队列、出手牌、扣能量、记进 `playerMoves` / `aiMoves`。
- **不做合法性校验**：录制时已经合法过一次，两端盘面一致，重放的是同一串事实。
- **对不上就中止**：手牌 / 区域里找不到记录的卡 id ⇒ 记一条红字、把该次重放标记为中断并把操作权交还玩家。
- 复盘期间玩家的一切操作入口被挡（`uiSnap` 单独挡，其余靠各自 `phase === 'play'` 的守卫）；影子模式则由玩家照常操作。

## 4. 易错点

- **建牌路径必须记进码里**：只记"12 张牌是什么"不够（见 §1）。
- **"牌一样"不等于"牌组一样"**：卡组顺序决定起手与卡牌 id，重放时绝不能再洗一次（见 §1）。
- **核对卡组的时机**：必须在两副牌都还是**完整 12 张**时比（`startRecord` 内）；晚一步就被抽掉 3 张，永远比不相等。
- **`decksOk` 里真正有判断力的是"对手牌组"**：我方牌组在 `defs` 模式下是按记录建的（按构造必然相等），
  而**对手牌组仍由种子派生**——随机流一旦错位、洗牌逻辑一旦变化，都会先在它上面暴露。
- **不符时只拒绝、不硬跑**：宁可中止并说明，也不要跑出一局"看起来正常"的假结果。
- **重放状态由 `restart` 每局显式设定或清空**：不靠"记得手动清"，否则会漏进下一局。
- **中止要保留现场**：把"本机算出来的"和"码里记的"整份打到控制台，否则无从排查。

## 5. 实时房间（PvP）

**通道**：`worker/`（Cloudflare Workers + Durable Object，一个房间一个 DO，绑定名 `ROOMS`）只做两件事——
转发消息、按 `(回合, 座位)` 去重；**不做裁判**（不校验合法性、不算分、不判胜负）。
客户端在 `js/net.js`（`window.Net`，`<script>` 放在既有脚本之后）：无构建、无依赖、不动既有加载次序。

**两端怎么算出同一局**（这是房间能成立的前提）：
- 本机恒坐 `p`、对手恒坐 `a` ⇒ 两端状态**互为镜像**，界面与全部文案都不用改；
- 镜像带来一个必须处理的坑：字面座位在两端指向不同的人，**同一颗随机数会派给不同的人**。
  故引擎里所有"按座位遍历、消耗随机数或决定先后"的地方一律走 **`state.seatOrder`（房间座位序：房主在先）**——
  单机恒为 `['p','a']`（行为与从前一字不差），联机时房主端 `['p','a']`、加入端 `['a','p']`。
  覆盖：**建牌顺序**（房主在先 ⇒ 卡牌 id 与卡组顺序两端一致）、洗牌 / 取牌 / 掷骰等按座位遍历、
  **翻牌先后的随机择方**、**状态指纹**，以及**放置队列的跨座位插序**（`canonicalizeFieldQueue`：
  两端的本回合入队先后天然相反，排成同一个顺序后，回合开始 / 回合结束的按时机 fx 才走同一条路）。

**握手**（双方各带一套满 12 张卡组）：
1. 各自连 `wss://<worker>/ws/<6 位房间码>?token=…`，房间分配 `host` / `guest`（同一个 token 回来还是原角色）；
2. 各发 `hello`：卡牌数据哈希 + 页面引擎指纹（本页所有 `<script src>` 源码的哈希）+ 本机 12 张卡组码；
   **哈希或指纹不一致 ⇒ 直接不开局**并提示 Ctrl+F5（这就是"数据哈希"与"引擎指纹"的用处）；
3. 双方都点「✅ 我已准备」后，由**房主定种子**发 `start`，两端据此 `restart({ netPvp: … })` 开局。

**每回合提交包**（`Game.net.localPackage`）：
`{ t:'turn', round, side, moves:[[卡牌编码, 区域]], fly:[[编码, 来源, 目标]], snap, retreat }`
- 落牌 / 移动用**卡牌编码**（`费用.档内下标`）而不是卡 id：编码由数据哈希兜住、与建牌顺序无关，更耐用；
- `side` 是**发送方**的本地座位：`p` ＝ 他自己那一手，`a` ＝ 他替对手托管的那一手；
- **加倍与认输另发即时消息**（`snap` / `retreat`）：对手当场就能决定要不要撤退（这是"加倍下回合生效"给的那个回合）；
  提交包里的同一标记随后幂等生效，两条路不会重复结算。

**每回合对账**：双方动作都灌完、翻牌之前（`reconcileRound`）各报一次**状态指纹**（按座位序取、键名用序位，
所以两端的码本身可比）。不一致 ⇒ 立刻停下并报出回合号与两个指纹——**分叉当场暴露**，不会闷到终局才发现分数对不上。

**超时判负**：等对手的提交包超过 `TURN_TIMEOUT`（90 秒）就**直接判他认输**——
本机不替他出牌、也不接管他的回合；同时发一条 `timeout` 告诉对手"你被判超时"（他若真掉线，这条自然发不到，
两端的结论仍然一致：谁没交包谁输）。判负走**认输**那条路，所以按撤退价结算（见 `docs/GAME_REFERENCE.md` §3）。

**不做断线重连**：刷新页面＝离开房间，对面会在超时后判你认输，本局结束（不再有"房间日志补跑"这一套）。

**限制**（有意为之，不是漏做）：
- **联机对局不生成挑战码**：码里还要带"谁执哪一边"的座位信息，现有格式装不下（点生成会说明；单机对局照常）。
- **没有防作弊**（阶段 3 不做）：两端各算一遍，改内存就能作弊；对账只能发现"算不到一起"，不能证明是谁改的。
- **掉线与慢网都按超时判负处理**：没有"托管代打"这条退路（原来是本机用 AI 替掉线方出牌，现已取消）。

## 6. 控制台探针

| 探针 | 用途 |
| --- | --- |
| `Game.dataHash()` | 本机数据（卡池 / 特殊卡 / 地形）的一致性哈希 |
| `Game._fingerprint()` | 状态指纹：回合 / 阶段 / 赌注 / 三块地形 / 放置队列 / 双方能量·手牌·牌库·三区·三个特殊牌池 |
| `Game._inputs()` | 这一局由哪些输入决定（双方卡组顺序 / 地形 / 起手 / 能量）——指纹不一致时先比它 |
| `Game._newGame(seed, opts)` | 设种子重开一局并等到「停在等你操作」，返回该时刻指纹；`opts.freshDeck` 强制默认曲线卡组、`opts.autoPass` 自动打完并返回终局指纹 |
| `Game._record()` | 本局录制内容（种子 / 数据哈希 / 建牌路径 / 双方卡组 / 逐回合动作） |
| `Game._code()` | 本局的一行挑战码 |
| `Game._replayInfo(code)` | 把一行码解回可读结构（与 `_record()` 同构，可直接 `JSON.stringify` 比对做往返验证） |
| `Game._replay(code, { mode })` | 重放：`review` 返回终局指纹；`shadow` 等到「轮到你」时交还控制权并返回那一刻指纹 |
| `Net.room()` / `Net.role()` / `Net.peerOnline()` | 联机：当前房间码 / 本机角色（`host`/`guest`）/ 对手是否在线 |
| `Game.net.localPackage('p', 回合, 认输?)` | 把某一方本回合的动作打成**提交包**（排查"到底发了什么"） |
