# 项目开发全局规则（东方逆转 · 纯前端卡牌游戏）

> 本文件是**全局开发规则**，所有改动（加卡、加机制、改数据、改文档）都必须遵守。
> **八条规则（优先级：★① 规则 1 最重要 → ★② 规则 6 次之 → 其余各条）**：
> ★① **只写当前内容，一切改动先精简（文档与代码注释同一取向）** ② 新卡取图流程 ③ 改动只写专项文档 + 每次改完补一条精简历史记录
> ④ 机制术语口径 ⑤ 数值记法「A-B = A 费 / B 战力」 ★⑥ **验证由用户负责，AI 不自行测试 / 不开浏览器 / 不读 AI 对战脚本代码**
> ⑦ 遇到不确定的概念或想法，先问用户 ⑧ 需求描述里的括号不是游戏内文本。
> 「当前状态」只写在各专项文档里：`docs/现有机制.md`（引擎机制）、`docs/现有地形.md`（地形）、
> `docs/现有人物卡牌.md`（人物卡）、`docs/现有特殊卡牌.md`（特殊卡 / token）、`docs/card-image-map.md`（卡图）。
> `docs/GAME_REFERENCE.md` 只保留跨模块总纲与**专项文档索引**；`docs/历史版本.md` 是**变更记录的唯一存放处**。

## 规则 1：只写当前内容，一切改动先精简 ★ 最重要的必须遵守的规范（文档与代码注释同一取向）

> 本条**最重要、必须遵守**，优先级高于其余各条；与其它规则冲突时以本条为准。

**一句话口径**：文档与代码注释都只讲**当前生效的内容**；不写版本号（`vNNN`）、不写历史修改过程、
不写"以前是怎样 / 已从 X 改成 Y"。**任何改动——改代码、改文档、追加历史记录——都必须"尽可能精简之后再进行修改和添加"**：
精简是**落笔前的前置动作**，不是事后清理。

- **不写**：`vNNN：…`（版本号前缀）、`（原 500ms）`、`首版只做了…`、`早期是…`、改动流水账——这些属于**变更记录**，归 `docs/历史版本.md`。
- **要写**：当前生效的规则一句话、与其它机制的**时序 / 优先级**、**例外与边界**（"此时不结算""并列全删""该字段为 0 时不能放牌"这类）、
  以及容易写错的地方（为什么这里不能写成某个更自然但错误的写法）。
- **篇幅**：能一行说清就一行；真正长的口径写在专项文档里，代码注释只留一句结论 + 指向文档 / 函数的锚点。
- **改文档**：**先把要写的内容精简好，再替换 / 追加**——专项文档直接写**当前口径**，不保留旧写法、不标版本号。
- **改角色 / 卡牌 / 机制**：**不再记录修改历史**，而是**用新的核心机制直接替换掉旧的核心机制**（旧口径从正文里消失，
  不做"原为…后改为…"的对照）。
- **变更留痕**：只写进 `docs/历史版本.md`，且同样**先精简再追加**——每条**一行**（版本号 + 改了什么，含关键数值与字段名），
  追加在**最上方**（新→旧）；不写实现细节、函数名、演出与 CSS 数值。
- 落到各文档的同步清单见规则 3。

## 规则 2：新卡图片的获取（优先自 assets/source-art 取图）

添加新人物卡（或给既有卡补图）时，**优先从项目根目录的 `assets/source-art/` 寻找该角色的图片**：

1. 在 `assets/source-art/` 中查找对应角色的立绘，命名形如 `240px-角色名（Q版立绘）.png`（素材为 **240×240**）。
   按角色名匹配，留意**简体 / 繁体写法差异**与**素材名 ≠ 卡牌名**的情况
   （如素材「因幡天为」对应卡牌「因幡帝」、素材「帕秋莉」对应卡牌「帕秋莉·诺蕾姬」）。
2. **找到后**：复制图片到 `assets/cards/` 并**改名为英文 / ASCII 文件名**（用角色常用罗马音或昵称，如 `hina.png`、`okuu.png`），
   然后在 `data/cards.js` 对应卡条目写 `img: '<文件名>'`。
3. **没找到**：**不要用其它图片顶替，也不要静默跳过**——必须**提醒用户**（报告缺哪张卡、缺哪个文件、检查过哪些候选），
   等用户把图片放进 `assets/source-art/` 后**再次检查**，确认接入再完成该卡。
4. 规格约定见 `docs/card-image-map.md`（512×512 正方形为佳，现有素材 240×240 可直接用；日后拿到更大的立绘再替换同名文件即可）。
   复制后**同步更新** `docs/card-image-map.md` 的文件名对照表，并在 `README.md`「已知待办（素材侧）」里删掉已补齐的角色。
5. 特殊卡（token，如石块 / 厄运 / 废弃列车）一般**没有图片**，用卡面 emoji 兜底即可，无需套用本条（除非用户另行提供 token 图片）。

## 规则 3：改动只写专项文档

**一句话口径**：地形 / 人物卡 / 特殊卡（token）/ 引擎机制的**清单与口径**只写在各自的专项文档里；
改完**不需要**再去 `docs/GAME_REFERENCE.md` 同步；**但每次改完都必须往 `docs/历史版本.md` 追加一条精简记录**（见下）。
（**精简、直接替换旧口径、不记修改历史**的要求见规则 1。）

- 新增 / 修改**人物卡** → 只更新 `docs/现有人物卡牌.md`（按费用分组、含张数总计；卡图见规则 2）；
- 新增 / 修改**特殊卡 / token** → 只更新 `docs/现有特殊卡牌.md`；
- 新增 / 修改**地形（区域）字段或地块** → 只更新 `docs/现有地形.md`；若带动引擎逻辑（新结算点 / 新术语），
  再同步 `docs/现有机制.md`（区域字段总表 + 机制段落 + 流程管线）；
- 新增**引擎机制 / 术语 / 演出 / 页面** → 只更新 `docs/现有机制.md`（§1 效果键表、§2 区域字段与口径、
  §5 数值口径、§6 其它已实装系统都要跟上）；
- 新增 / 替换**卡图素材** → 更新 `docs/card-image-map.md` 的文件名对照表与素材现状，以及 `README.md`「已知待办（素材侧）」；
- **`docs/GAME_REFERENCE.md`**：只保留**跨模块总纲**（一局怎么打、牌库与抽牌、胜负与赌注）与**指向专项文档的索引**；
  不要再往里填地形表 / 卡牌表 / token 表 / 效果键表 / 逐机制口径。
- **`docs/历史版本.md`（每次修改后都要补一条）**：专项文档改完后，**恢复继续往 `docs/历史版本.md` 追加记录**的做法——
  取**下一个版本号**，把这次改动**先精简成一句话**（版本号 + 改了什么，含关键数值与字段名），追加在**表格最上方**（新→旧）；
  不写实现细节、函数名、演出与 CSS 数值（写法与理由见规则 1）。

## 规则 4：机制术语口径

- **揭示**（On-Reveal）= 此牌翻开时立刻执行的一次性效果；
- **持续** = 此牌翻开后持续存在的效果（源卡离场即失效）；
- **防摧毁**（`surv`）= 被摧毁时不离场、取而代之永久 −N 战力；
- 术语的完整口径与各机制细节见 `docs/现有机制.md`。

## 规则 5：数值与卡牌的记法口径

**一句话口径**：用户口述数值时，「**A-B**」（如「1-2」「5-10」）读作 **A 费 / B 战力**——
**横杠前是费用（能量消耗 `c`），横杠后是战力（威力 `p`）**。

- 例：「1-2」= 1 费 / 2 战力（桑尼米尔克）；「2-3」= 2 费 / 3 战力（藤原妹红）。
- **不要**把横杠理解成区间（本游戏数值都是定值），也不要读成「战力-费用」——**永远 费用 在前、战力 在后**。
- 文档与回复里提到既有卡也用这套简写：**「A费/B战力」**（可写作 `A费/B力`）。
- **落位归属按费用**：往 `data/cards.js` 的 `POOL` 加卡时放进**它费用的那一档**（如 1 费卡进 `POOL[1]`）；
  改费用意味着**在池子里搬家**，并影响「妖精神社」等按费用抽卡的机制（见 `docs/现有机制.md` 的 `spawn.cost`）。
- 改数值时一并检查的联动：AI 与玩家兜底牌库的费用曲线（每档要够抽）、图鉴 / 卡组页 / 开发者「指定卡牌」的费用筛选档、
  `docs/现有人物卡牌.md` 的分组与总数、`docs/card-image-map.md` 的费用列。

## 规则 6：验证由用户负责，AI 不自行测试 / 不开浏览器 / 不读 AI 对战脚本代码 ★ 重要性第二（仅次于规则 1）

> 本条**重要性第二**，优先级高于规则 2~5 与 7~8；与其它条冲突时以本条为准（规则 1 优先于本条）。

**一句话口径**：改完代码**不要自己跑测试、不要自己开浏览器 / 起服务器验证**——一律**由用户亲自检测**；
**AI 对战脚本相关的代码与 `tests/` 下的冒烟 / 回归脚本，除非用户明确要求，一律不要阅读**。

- **不读 AI 对战脚本相关代码**（`js/ai.js` 及对手 AI 相关的其它代码）：除非用户**明确要求**，不要阅读、不要顺手通读
  —— 那部分暂时用不到修改，读了只会浪费 token；其它需求顺带牵涉到 AI 代码时也不主动展开。
- **不读 `tests/smoke-test.js`**（以及 `tests/` 下任何冒烟 / 回归脚本）：不阅读、不运行、不据此推断口径。
- **不执行**：`npm test` / `node tests/smoke-test.js`、用 headless 浏览器或自动化脚本
  打开页面、起本地静态服务器（`python -m http.server` / `npx serve` 等）。
- **不做任何烟雾测试、不开浏览器测试**：**一切效果由用户检测**——AI 只做静态改动与静态自查。
- **允许**（纯静态检查）：读代码 / 文档、`grep` / `glob` 检索、不产生运行的语法或数据自检
  （如确认 `data/*.js` 字段写法一致、静态清点张数）——只要不启动运行时、不开浏览器就行。
- **交付方式**：回复里列出**改动文件清单**与**建议用户验证的步骤 / 现象**。
- 用户检测后会把现象 / 报错贴回来，据此再改；不要用"我测过了"替代用户的实测结论。

## 规则 7：遇到不确定的概念或想法，先问用户

**一句话口径**：需求 / 机制 / 数值口径上有**任何不确定**（新机制边界、与既有机制的相互作用、命名与术语、演出节奏、是否要动文档等），
**先向用户提问确认**，不要自行猜一个版本闷头实现。

- **该问**：① 需求涉及既有机制但没说如何交互（与 `surv`/`phx`/`prot`/`fieldQueue` 的时序等）；
  ② 术语或命名有多种合理解释；③ 数值 / 概率 / 回合数等待定；④ 会动到多个模块或既有卡牌平衡；
  ⑤ 无法从专项文档与代码确定"当前口径是什么"。
- **不必问**：纯粹的机械改动（改数值、补文档、按既有口径新增一张同构的卡 / 地形），以及能从文档与代码直接读出既定口径的情况
  ——按既有口径做，并在回复里说明依据。
- **怎么问**：把**候选方案与各自影响**一并列出（尽量给推荐项），让用户一次拍板。

## 规则 8：需求描述里的括号是给我的说明，不是游戏内文本

**一句话口径**：用户用文字描述**新地形 / 新角色**（或新 token、新机制）时，**括号外**的内容＝游戏里**实际显示的信息**；
**括号内**的内容只是**方便我理解**的补充说明，**不要写进游戏内显示文本**。

- 适用范围＝**游戏内会展示的文字**：地形的 `eff`、卡牌的效果文本 `t`、token 的效果文本，以及由这些文字派生的弹窗 / 提示文案。
- 括号里的说明该去哪：若它属于**机制口径本身**（结算时机、边界、与既有机制的交互），按规则 3 写进**专项文档**的实现说明里；
  **游戏内文本一律不带上它**。
- 例（文字）：用户说「此区域双方已翻开的卡每回合 −1（暗牌不算，翻面后才开始吃衰减）」，游戏内显示的就是括号前那句
  「此区域双方已翻开的卡每回合 −1」。
- 例（名字）：用户说「加一张 幽幽子（西行寺家的公主）」，游戏内卡名就是括号前的「幽幽子」。
- 判断方法：**括号＝给我的说明**；拿不准时按规则 7 先问用户。编写保持**简洁**（同规则 1）——游戏内文本是给玩家一眼看懂的。
