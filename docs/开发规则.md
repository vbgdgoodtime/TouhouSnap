# 项目开发全局规则（东方逆转 · 纯前端卡牌游戏）

> 本文件是**全局开发规则**，所有改动（加卡、加机制、改数据、改文档）都必须遵守。
> 六条规则：① 新卡取图流程 ② 改动只写专项文档 ③ 机制术语口径 ④ **数值记法「A-B = A 费 / B 战力」**
> ⑤ **验证由用户负责，AI 不自行跑测试/开浏览器** ⑥ **遇到不确定的概念或想法，先问用户**。
> 「当前状态」的说明**只写在各专项文档**里：`docs/现有机制.md`（引擎机制）、`docs/现有地形.md`（地形）、
> `docs/现有人物卡牌.md`（人物卡）、`docs/现有特殊卡牌.md`（特殊卡/token）、`docs/card-image-map.md`（卡图）。
> `docs/GAME_REFERENCE.md` **不再重复收录**以上内容，只保留跨模块总纲与**专项文档索引**。

## 规则 1：新卡图片的获取（优先自 /assets/source-art 取图）

添加新人物卡（或给既有卡补图）时，**优先从项目根目录的 `assets/source-art/` 文件夹寻找该角色的图片**：

1. 在 `assets/source-art/` 中查找对应角色的立绘，命名通常形如
   `240px-角色名（Q版立绘）.png`（**v178 起素材为 240×240 清晰版**；早期素材为 `100px-角色名（Q版立绘）.png`，
   历史文件按原名保留、不追溯改名。按角色名匹配，留意**简体/繁体写法差异**与**素材名≠卡牌名**的情况，
   如素材「因幡天为」对应卡牌「因幡帝」、素材「帕秋莉」对应卡牌「帕秋莉·诺蕾姬」）；
2. **找到后**：复制该图片到 `assets/cards/` 目录，并**改名**为英文/ASCII 文件名
   （惯例用角色常用罗马音/昵称，如 `hina.png`、`okuu.png`），然后在
   `data/cards.js` 对应卡条目标记 `img: '<文件名>'`；
3. **没有找到**对应角色的图片：**不要用其它图片顶替，也不要静默跳过**——
   必须**提醒用户**（报告缺哪张卡、缺哪个文件、我检查过哪些候选），
   由用户重新下载图片放入 `assets/source-art/` 后，**再次检查图片是否存在**，确认接入后再完成该卡；
4. 图片规格约定见 `docs/card-image-map.md`（512×512 正方形为佳；`assets/source-art/` 内现为
   **240×240** Q 版立绘（v178 前为 100px），可直接复制使用——放大视图按 240 显示已够清晰，
   日后若拿到更大的立绘（512×512）再替换同名文件即可；复制后**同步更新 `docs/card-image-map.md`
   的文件名对照表与素材状态**，并在 `README.md`「已知待办（素材侧）」里划掉已补齐的角色）。
5. 特殊卡（token，如石块/厄运/废弃列车）一般**没有图片**，用卡面 emoji 兜底即可，
   无需套用本条；除非用户另行提供了 token 图片。

## 规则 2：改动只写专项文档，`GAME_REFERENCE.md` 不再重复收录（v168 起）

**一句话口径**：地形 / 人物卡 / 特殊卡（token）/ 引擎机制的**清单与口径**只写在各自的专项文档里；
改完这些内容**不需要**再去 `docs/GAME_REFERENCE.md` 同步一遍——它只保留跨模块总纲（一局结构 /
牌库与抽牌 / 胜负与赌注）与一份**指向专项文档的索引**。

- 新增/修改**人物卡** → 只更新 `docs/现有人物卡牌.md`（按费用分组、含张数总计；卡图另见下条）；
- 新增/修改**特殊卡 / token** → 只更新 `docs/现有特殊卡牌.md`；
- 新增/修改**地形（区域）字段或地块** → 只更新 `docs/现有地形.md`；若该字段牵动引擎逻辑（新增结算点/
  新机制/新术语），再同步 `docs/现有机制.md`（区域字段总表 + 机制段落 + 流程管线）；
- 新增**引擎机制 / 术语 / 演出 / 页面** → 只更新 `docs/现有机制.md`（其 §1 效果键表、§2 区域字段与口径、
  §5 数值口径、§6 其它已实装系统都要跟上）；
- 新增/替换**卡图素材** → 更新 `docs/card-image-map.md`（文件名对照表 + 素材状态）与 `README.md` 的
  「已知待办（素材侧）」；
- **`docs/GAME_REFERENCE.md`**：除总纲外**不要**再往里填地形表 / 卡牌表 / token 表 / 效果键表 / 逐机制口径；
  只有**跨模块、跨文档的总纲**（一局怎么打、牌库与抽牌、胜负与赌注）改动才动它。其 **§5 历史更新记录
  已于 v167 封存**——正文**已迁出并精简**到 **`docs/历史版本.md`**（历史记录的**唯一存放处**，
  v1 ~ v167 逐版本精简记录 + 版本段主题概览），GAME_REFERENCE 的 §5 只保留指向它的索引；
- 各专项文档内部保留**行内版本标记**（如「v153 起…」「v164 新增」），改动时在对应条目上标注版本号即可
  ——这就是当前唯一的“变更留痕”方式（替代过去在 GAME_REFERENCE 更新记录里逐条补写）。
- **历史记录只放 `docs/历史版本.md`**（v168 起）：该文件是历史变更记录的**唯一存放处**，收录
  **v1 ~ v167 的精简版逐版本记录**（从 GAME_REFERENCE §5 迁出）；**v168 起不再逐版本记录新改动**，
  日常改动**不要**去 `docs/历史版本.md` 追加条目（留痕走上面的行内版本标记）。`docs/GAME_REFERENCE.md` §5 只保留
  指向该文件的**索引**；若日后确需恢复逐版本记录，先与用户确认。
- 版本号：全局共用一条递增序列（当前最新为 **v204**），新增改动就取下一个号，专项文档里的行内标记与之对齐。

## 规则 3：机制术语口径（v58/v59/v60 起）

- **揭示**（原「现身」）= 此牌翻开时立刻执行的一次性效果，后续不再触发；
- **持续**（原「在场光环」）= 此牌翻开后持续存在的效果（如天子→己方石块）；
- **防摧毁**（`surv`）= 被摧毁时不会离场、取而代之永久 −N 战力；
- 术语的完整口径与各机制细节见 `docs/现有机制.md`（规则 2 起不再在 `GAME_REFERENCE.md` 复述）；
- 历史记录（`docs/GAME_REFERENCE.md` §5，已封存）里的旧称与旧数值保留当时写法，不做追溯改写。

## 规则 4：数值与卡牌的记法口径（v169）

**一句话口径**：用户口述卡牌数值时，「**A-B**」（如「1-2」「2-3」「5-10」）读作 **A 费 / B 战力**——
**横杠前是费用（能量消耗 `c`），横杠后是战力（威力 `p`）**，即「费用-战力」。

- 例：「1-2」= **1 费 / 2 战力**（桑尼米尔克）；「2-3」= **2 费 / 3 战力**（如藤原妹红）；
  「5-10」= 5 费 / 10 战力（伊吹萃香，v167 起）。
- **不要**把横杠理解成「战力区间」或「费用区间」（本游戏卡牌数值都是定值，不存在区间）；
  也不要反过来读成「战力-费用」——**永远是 费用 在前、战力 在后**。
- 同理，文档与回复里提到既有卡时也用这套简写：**「A费/B战力」**（可写作 `A费/B力`）；
  逐版本的历史记录里沿用的旧写法（如「5费/12战力」）不追溯改写。
- **落位归属按费用**：往 `data/cards.js` 的 `POOL` 里加卡时，卡牌放在**它费用的那一档**
  （如 1 费卡进 `POOL[1]`）；改费用就意味着**在池子里搬家**，且会影响「妖精神社」等按费用抽卡的机制
  （见 `docs/现有机制.md` 的 `spawn.cost`）。
- 相关联动口径（改数值时一并检查）：AI 与玩家兜底牌库按费用曲线取卡（每档需要够抽）、
  图鉴/卡组页/开发者「指定卡牌」的费用筛选档、`docs/现有人物卡牌.md` 的分组与总数、
  `docs/card-image-map.md` 的费用列。

## 规则 5：验证由用户负责，AI 不自行测试、不开浏览器（v168）

**一句话口径**：改完代码**不要自己跑测试、不要自己开浏览器/起服务器验证**——一律**由用户亲自检测**；
改了哪些文件、期望看到什么现象，**说清楚交给用户去验**即可。

- **不执行**：`npm test` / `node tests/smoke-test.js`（`tests/` 下的任何冒烟/回归脚本）、
  用 headless 浏览器或自动化脚本打开页面、起本地静态服务器（`python -m http.server` / `npx serve` 等）
  来"自己看一眼"。这些都属于**用户负责的验证环节**。
- **允许**（静态检查，不产生运行、不碰页面）：读代码/文档、`grep`/`glob` 检索、纯静态的语法或数据自检
  （如确认 `data/*.js` 的字段写法与前文一致）——只要不启动运行时、不开浏览器就行。
- **交付方式**：改完后在回复里列出**改动文件清单**（如 `data/cards.js`、`js/game.js`、`docs/现有机制.md`）
  与**建议用户验证的步骤/现象**（例如"用开发者「🗻 指定地形」换上某地形后，观察第 N 回合末的日志与点数"）。
- **用户会反馈问题**：用户检测后会把现象/报错贴回来，据此再改；不要用"我测过了"来替代用户的实测结论。

## 规则 6：遇到不确定的概念或想法，先问用户

**一句话口径**：需求/机制/数值口径上有**任何不确定**（新机制的边界、与既有机制的相互作用、
命名与术语、演出或节奏、是否要动文档等），**先向用户提问确认**，不要自行猜一个版本闷头实现。

- **该问的情形**：① 需求涉及既有机制但没说明如何交互（如新效果与 `surv`/`phx`/`prot`/`fieldQueue`
  时序的关系）；② 术语或命名有多种合理解释（如把「1-2」当成战力区间）；③ 数值/概率/回合数等待定；
  ④ 会动到多个模块或既有卡牌平衡；⑤ 无法从 `docs/` 专项文档与代码中确定"当前口径是什么"。
- **不必问的情形**：纯粹的机械改动（改数值、补文档、按既有口径新增一张同构的卡/地形）、
  以及能从专项文档与代码中直接读出既定口径的情况——按既有口径做，并在回复里说明依据。
- **怎么问**：把**候选方案与各自影响**一并列出来（尽量给出推荐项），让用户一次就能拍板；
  宁可多问一句，也不要交付一个方向错误的实现。确认后再动手，实现完按规则 5 交给用户检测。
